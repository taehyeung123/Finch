## 5. 기각한 의견과 이유

1. **검토 2-4 — 쓰지 않는 두 칸을 방침 항목에 추가하거나 칸을 지우라.** 코드 어디서도 읽거나 쓰지 않아 기본값(0)만 있는 칸이라 «수집하는 항목»이 아닙니다. 방침에 넣으면 오히려 사실과 다릅니다. 칸 삭제는 법률 문서 작업의 범위 밖입니다(나중에 그 기능을 살리면 그때 항목을 추가).
2. **검토 2-1의 대안 — «결제 운영 안 함»을 코드 스위치로 강제하라.** 결제 화면은 이미 토스 키가 없으면 열리지 않습니다(2-2). 토스 배관은 페이앱으로 바뀔 예정이라 고치지 않는다는 결정(2026-09-07)도 있습니다. 필요한 것은 새 스위치가 아니라 «운영 환경에 토스 키가 없다»는 확인입니다(7절 3번).
3. **초안의 «광고성 정보 수신: 기존 값으로 미리 체크»(5-2).** 검토 1-7이 옳다고 보고 버렸습니다(4절).
4. **초안의 «방명록 안내 / 폼 동의 문구에 이메일을 직접 적기».** 문구는 반영했지만 주소는 `lib/legal/business.ts` 에서 읽게 했습니다 — 초안 자신의 «하드코딩 금지» 메모와 같은 이유입니다(기각이라기보다 방식 변경).

## 6. 배포·운영 순서

1. **배포 직전(9/12)**
   - **0095 를 SQL Editor 에서 먼저 적용한다(권장).** 표·인덱스를 더하기만 하는 파일이라 지금 돌고 있는 옛 코드는 영향이 없다 — 먼저 넣는 쪽이 가장 안전하다.
     깜빡하고 코드가 먼저 나가도 **아무도 갇히지 않는다**(2차에서 확인·보강):
     동의 저장은 `user_consents`(0079)로 그대로 되고 이력 함수는 던지지 않는다 · 광고성 정보 스위치는 켜고 끄기가 되고 하루 상한만 꺼진다 ·
     메타 삭제 요청의 후속 삭제 대상은 표 대신 «0095 적용 필요» 로그에 회원 id 와 함께 남는다 · 상태 페이지·크론은 그 부분만 건너뛴다.
     손실은 «증빙·알림»이지 «이용»이 아니다. 늦게 넣었다면 그 사이 로그의 삭제 대상을 13절 4번 표에 옮겨 적는다.
     (0079 자체가 없는 DB 는 게이트가 «모름 → 통과»이고, 확인 없는 즉시 삭제도 2차부터 닫힌다.)
   - 이 브랜치를 합치고 `npm run build` · `npm run lint` 를 돌린다(이 작업은 워크트리 규칙상 빌드를 돌리지 않았다 — 12절).
     `lib/legal/versions.ts` 의 날짜 불변식이 어긋나면 이 빌드가 멈춘다.
2. **9/12 배포**(2차: 9/14 → 9/12로 당김)
   - 날짜가 코드에 박혀 있다: 방침 «공개일·시행일 9/12», 약관 «공고 9/12 · 시행 9/22». **배포가 9/13 이후로 밀리면** `TERMS_ANNOUNCED`·`PRIVACY_VERSION` 을 실제 배포일로 바꾸고 배포한다
     (과거 날짜로 «게시했다»고 적으면 사실이 아니다). `TERMS_VERSION`(9/22)은 배포가 9/15 까지면 그대로 둬도 공고 7일이 지켜지고, 그보다 늦으면 불변식이 빌드를 멈추니 함께 미룬다.
   - 배포 뒤 확인: `/terms`, `/terms/operation`, `/terms/refund`, `/privacy`, `/terms/changes`, `/privacy/changes`, 두 보관 페이지, 푸터의 «사업자정보확인» 링크가 열리는지, 로그인 뒤 화면에서 GA 요청(googletagmanager·google-analytics)이 나가지 않는지(브라우저 개발자 도구 네트워크 탭 — 앱 화면 → 요금제 비교 → **뒤로** 도 한 번, 11절).

   - **심사 계정 미리 동의** — 메타 심사용 계정(OWNER_EMAIL 의 두 번째 이후 주소)마다 로그인해 상단 띠의 «미리 동의하기»를 누른다. 안 하면 녹화에 띠가 나오고, 9/22 부터는 심사관이 동의 화면을 만난다
     (게이트는 법적 장치라 코드로 심사 계정만 빼지 않는다).
3. **9/12 ~ 9/21** — 옛 약관 동의 회원에게 앱 상단 띠가 배포 즉시 자동으로 뜬다(배포 외 할 일 없음).
4. **9/22 0시(한국 시간)** — 동의 화면 게이트가 자동으로 선다(날짜로 판정, 배포 불필요). 그 시각에 열려 있던 탭도 다시 그려져 게이트가 선다(2차).
5. **10/22 무렵** — 아직 동의하지 않은 회원에게 부칙 제2조의 개별 안내 메일(13절 2번). 메일에 «11월 21일까지 거부 의사를 밝히지 않으면 동의한 것으로 봅니다»를 분명히 적는다.
6. **상시**
   - 메타 삭제 요청이 들어오면 요청 7일 뒤~10일 안에 남은 정보 삭제(13절 4번). 대기 중인 건이 있으면 retention 크론이 매일 아침(04:20 KST) Sentry 오류로 알린다.
   - 광고성 정보 처리 결과 메일 실패 로그(`user=…` 가 적힌 줄)가 보이면 14일 안에 다시 보낸다(13절 6번).
   - `[refund-owed]` 알림이 오면 결제대행사 관리 화면에서 그 주문을 부분 취소한다(13절 7번). 지금은 결제가 열려 있지 않으면 올 일이 없다.

**공고 기간 판단(2차 확인)** — 7일 공고의 근거는 새 약관 제3조③1(«적용일 7일 전부터»)이고, 코드가 7일 미만을 막는다.
새 약관 제3조③2는 «불리하거나 중요한 변경은 30일 전부터»인데, 이 30일은 **간주동의**(거부하지 않으면 동의로 봄)의 요건이다(제3조④).
이번 개정은 기존 회원에게 불리한 변경을 **명시적 동의로만** 적용하고(동의 전까지 종전 약관 — 부칙 제2조), 간주동의는 시행 30일 뒤 개별 통지 + 다시 30일 뒤라
공고일부터 70일(11/21)이 넘는다. 새 가입자는 가입할 때 새 약관에 직접 동의한다. 그래서 30일이 필요한 변경은 없다고 판단했다 —
다만 «동의하지 않으면 이용할 수 없다»는 게이트가 사실상 강제가 아닌지는 변호사 쟁점 5번이다. 종전 약관(7/16)의 개정 조항은 «적용일자와 사유를 명시하여 사전 공지»뿐이라 기간을 정하지 않았다.
변호사가 30일을 요구하면 `TERMS_VERSION` 하나만 `2026-10-12` 로 바꾸면 된다(게이트·띠·문서·부칙이 함께 따라간다).

## 8. 결제를 열기 전 (필수)

1. **결제대행사 확정(페이앱)** — 방침 제7조 «결제대행사» 행에 법인명·위탁 업무를 적고(국외 이전이면 제8조도), 시행 7일 전에 공지.
2. **결제 확인 메일** — 결제(자동 결제 회차 포함)마다: 상호·대표자·주소·전화·이메일, 요금제·내용, 금액·결제수단·다음 결제일, 청약철회 기한·방법·효과, 환불·지연배상 조건, 불만·분쟁 처리, 약관 링크(전자상거래법 제13조②, 약관 제28조①). 만든 뒤 `checkoutNoticeLines` 에 «결제가 끝나면 결제 확인 메일을 보내 드려요» 한 줄 추가.
3. **플랜 관리의 「청약철회」 버튼**(약관 제28조④) — 구매와 같은 방법으로 철회할 수 있어야 합니다(전자상거래법 제21조의2).
4. **상위 요금제 변경·약관 거부 탈퇴 시 남은 기간 일할 환불 자동화**(약관 제24조①·제3조⑤) — 2차에서 확인: `changePlan` 은 새 요금제 전액만 청구하고
   옛 요금제의 남은 날을 돌려주지 않았고, 재동의 화면의 탈퇴(`withdrawFromConsent`)는 환불 없이 계정을 지웠다. 환불정책 페이지의 계산 예시(«Creator 10일째 Pro 변경 → 6,600원 환불»)가
   현재 사실처럼 적혀 있었다. 지금은 두 곳이 계산한 금액·주문번호를 `[refund-owed]` 알림으로 올리고(요금제 변경 알림 문구에도 환불 금액을 적는다) **사람이 부분 취소**한다(13절 7번).
   토스 배관은 교체 예정이라 자동 부분 취소를 붙이지 않았다 — 새 결제대행사 연동 때 `lib/billing/refund-owed.ts` 의 알림 자리를 부분 취소 호출로 바꾼다.
5. **결제 기록 별도 보존** — 지금은 탈퇴 시 같은 표에서 회원 id만 비웁니다(`0044_preserve_payment_records.sql`, 검토 1-21). 별도 보존 표(service_role 전용)로 옮기고 5년 뒤 파기. 결제 관련 문의는 탈퇴 시 3년 분리 보관(지금은 함께 삭제).
6. **부가세 표시**(7절 11번).
7. **결제 화면** — 새 결제 화면에도 `checkoutNoticeLines` 와 환불정책·이용약관 링크, 미리 체크하지 않은 필수 동의를 그대로 씁니다. 호출하는 곳이 없는 옛 위젯 화면(`/settings/billing/checkout`)은 쓰지 않을 거면 지웁니다.

## 9. 권장 개발 작업

1. **메타 삭제 콜백 범위 확대** — 연결 삭제와 함께 그 채널의 남은 정보(자동 DM 규칙·발송 기록, 광고 변경 기록, 발행 식별값, 알림, 프로필 링크 게시물 미리보기)를 지운다. 그러면 7절 7번 수작업이 없어진다.
   2차 현황: 대상은 `data_deletion_followups` 에 쌓이고 크론이 매일 알린다. 자동 삭제는 넣지 않았다 — 알림·발행 식별값은 채널 칸이 없어 기계적으로 가를 수 없고,
   되돌릴 수 없는 삭제를 운영 DB 드라이런 없이 크론에 넣지 않는다. 넣을 때는 요청 7일 뒤(자동 DM «댓글당 1회» 가드가 7일 답장 창 안에서 유지되게), 요청 시각 **이전** 행만.
2. **가입을 마치지 않은 계정 24시간 뒤 삭제** — 7절 6번 결정 뒤. 먼저 드라이런.
3. **방문 통계 최소화** — Upstash 로 보내는 방문자 구분값 제거(또는 매일 바뀌는 키), 도시를 시·도로 축소(위치정보법 논점 축소). 하면 방침 제3조④·제8조 수정.
4. **팀 초대 취소·내보내기 시 이메일 삭제** — 행을 바로 지우면 초대 속도 제한(최근 초대 행 수)이 풀려 초대 메일 스팸이 가능해진다. 이메일만 지우거나 해시로 바꾸는 식으로 설계.
5. **storage-sweep 삭제 단계 켜기** — 화면에서 지운 이미지를 30일 안에 삭제. 하면 방침 제4조 «화면에서 지운 이미지» 행 수정.
6. **광고성 정보 2년 재확인** — 첫 도래 2028-09. 동의 이력(0095)으로 대상 산출.
7. **Apify 를 운영에 넣으면** 방침 제7·8·10조에 추가.
8. **비공개 서류** — 수탁사 DPA 수락 기록(Supabase·Vercel·Sentry·Upstash·Resend·Anthropic·Google), 내부 관리계획(선택), AI기본법 고영향 AI 해당 여부 검토 기록, 개인정보취급자 접속기록 보관, 침해사고 신고 절차.
9. **약관 사본 이메일 요청(제3조①)·위탁 정보 처리 현황 문의(제20조①6, 30일) 응대 절차** — 고객센터 매크로로 준비.
10. **(2차 보류) 동의 상태 표를 서버만 쓰게** — `user_consents` 는 0079 의 insert/update 정책으로 본인이 PostgREST 로 직접 고칠 수 있다(이력·처리 결과 메일 없이).
   정책을 지우면 **지금 돌고 있는 옛 코드의 가입 동의 저장이 막혀 새 가입자가 동의 화면에 갇힌다** — 배포 순서에 따라 잠김이 생기는 변경이라 이번에 넣지 않았다.
   할 때는 ① 코드의 동의 쓰기를 `createAdminClient()` + `.eq("user_id", …)` 로 옮겨 배포하고 ② 그 **뒤에** 정책을 지우는 마이그레이션을 따로 넣는다(순서 고정).
   그 전까지 앱 밖 수정은 13절 9번 쿼리로 찾는다(고칠 수 있는 것은 본인 행뿐이고, 남의 기록은 못 고친다).
