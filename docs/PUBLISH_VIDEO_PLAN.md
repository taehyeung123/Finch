### 되는 것 (사장님 요구 2026-09-11 대조)

- 새 메타 권한은 필요 없다(이미 받는 발행 권한 두 개가 전부 덮는다 — §한 줄 요약). 서버에서 영상을 변환하지 않는다:
  MP4·MOV(H.264/HEVC 영상 + AAC 소리)만 받고, 길이·해상도·코덱·프레임·소리를 **고르는 즉시 브라우저가 검사**한다.
  지금 규칙으로 못 올리는 영상은 올리지 않고 «보류»한다(300MB 를 다 올린 뒤에 거절하지 않게). 최종 판정은 메타이고, 메타의 거절은 한국어로 바꿔 보여 준다.
- 영상은 메타가 몇 분씩 처리한다 — 글이 «처리 중»으로 내려앉고 매분 크론이 이어 올린 뒤 알림을 보낸다. 같은 글을 두 번 올리지 않는다(발행 호출 전에 시도 기록을 먼저 적는다).

### 2026-09-12 점검 수리 (`feat/video-final`)

점검 셋(보안·데이터 / 엔진 / 화면) 중 보안·데이터는 «발견 없음». 나머지를 이렇게 고쳤다:

1. **처리 시간 초과 뒤 «다시 시도»가 곧바로 또 실패했다.** 처리 마감이 준비물에 붙어 있어서, 마감을 넘겨 실패한 글을 다시 시도하면
   상태를 한 번 읽고 같은 (이미 지난) 마감으로 또 실패했다 — 준비물 수명(23시간)이 끝날 때까지 «다시 시도»가 먹지 않았다.
   이제 마감은 **시도마다** 연다: 첫 창을 넘기면 준비물은 남기고 마감만 비운다 → 다시 시도하면 새 창이 열리고, 그사이 끝난 준비물은
   파일을 다시 받아 가지 않고 그대로 올라간다. 다시 연 창마저 넘기면 그 준비물은 메타 쪽에서 멈춘 것으로 보고 버린다(다음 시도가 새로 만든다).
   (`engine-core.ts` «처리 창», `isExtendedDeadline` / `run.ts` `endWindow`)
2. **인스타 2207008 처리.** 메타 오류 표(2026-09-12 다시 확인)는 이 코드의 뜻을 «그 준비물이 없거나 만료됐다», 권고를 «발행 때의 일시 오류, 30초~2분 안에 1~2번 다시»로 적는다.
   - 만들기·발행에서 오면 권고대로 잠시 뒤 다시 부른다 — 다시 부르기 전에 상태부터 읽는다.
   - **상태를 읽을 때** 오면 그 준비물은 정말 없다 → 만료로 보고 새로 만든다(발행 시도 전일 때만). 예전엔 «상태 모름»으로 읽어 죽은 준비물을 마감까지 붙잡고 있었다.
   - 같은 표의 2207053(«알 수 없는 업로드 오류», 권고 «새 준비물을 만들라»)이 발행 때 오면 같은 준비물을 또 부르지 않고 버린다.
   - 준비가 끝났는데 발행이 «잠시 뒤에»로 계속 거절되면 끝이 있다: **처리 마감과 발행 시각 중 늦은 쪽 + 15분**이 지나면 실패로 멈추고 알린다
     (`publishRetryEndMs`). 예전엔 끝이 없어 매분 불렀다(23시간마다 새 준비물로 되풀이).
3. **작성기**: 형식이 틀린 파일과 개수 초과를 한 번에 고르면 두 이유를 다 말한다(예전엔 개수 문구가 형식 문구를 덮었다).
4. **목록 썸네일**: 서명 주소(1시간)가 만료돼 깨지면 깨진 그림 대신 종류 아이콘으로 물러난다 — 발행 목록과 «내 콘텐츠» 둘 다(`components/ui/signed-thumb.tsx`).
5. **문구**: 발행 화면의 «데모 모드에서는 …» → «지금은 예시 화면이라 …»(운영 용어 금지 규칙). 처리 시간 초과 문구의 «영상을» → «게시물을»(사진만인 글도 같은 마감에 걸린다).

### 2026-09-12 계정 전환 — 글마다 «대상 계정»(`feat/publish-account`, 마이그레이션 0094)

사장님 지적: 연결된 인스타 계정을 다른 계정으로 바꾸면(재연결은 connected_accounts 의 같은 행을 제자리에서 고친다) 목록에 옛 계정 글이
섞여 보이고 어느 글이 어느 계정 것인지 모른다. **더 나쁘게는 A 로 예약한 글이 B 로 바꾼 뒤 B 로 올라갔다** — 엔진이 발행할 때마다
지금 연결된 계정의 토큰을 썼기 때문이다. 규칙의 정본은 `lib/publish/account-core.ts` 머리말이다.

- **대상 계정**(`scheduled_posts.account_platform_id`·`account_handle`, 서버 전용 칸): 사용자가 «발행을 약속한 순간» 연결돼 있던 계정.
  새 글의 예약·지금 발행(`createPost`·스튜디오 예약 라우트), 초안·실패 글의 예약하기·다시 예약(`scheduleDraft`), 「지금 발행」(`publishNow`)이
  그 순간의 계정을 적는다(`lib/publish/account.ts` stampPostTarget). 초안은 대상이 없다(예약하는 순간 정해진다). 발행을 **시도한 뒤**의 글은 절대 바꾸지 않는다.
- **엔진**(`run.ts`·`engine-core.ts` ⓪): 대상 계정 ≠ 지금 연결된 계정이면 메타를 한 번도 부르지 않고 실패 + 알림 —
  «예약할 때 연결돼 있던 @A 계정이 아니라 지금은 @B 계정이 연결돼 있어요 — 새 계정으로 올리려면 다시 예약해 주세요».
  시도한 뒤라면 «올라갔는지 확인하지 못했어요 — @A 계정에서 먼저 확인…»(두 번 올리지 않는다). 대상이 빈 옛 글은 지금 계정으로 나가며 그 계정을 적고,
  올라가면 실제로 올린 계정(id·지금 이름)을 적는다.
- **연동 콜백(인스타·스레드)**: 옛 계정과 다른 계정으로 다시 연결하면 ① 행을 고치기 **전에** 대상이 빈 글(초안 제외)에 옛 계정을 적고
  ② 행을 고친 **뒤에** 옛 계정 대상의 예약·처리 중(발행 시도 전) 글을 곧바로 실패로 내린다(«계정을 바꿔서 발행하지 못했어요 — 새 계정으로 올리려면 다시 예약해 주세요»).
  ① 이 실패했어도 새지 않게, 바꾸기 시작 전에 잡힌 **대상 없는** 예약도 같이 내리며 옛 계정을 적는다(예약은 연결이 있어야 잡히므로 새 계정 것이 아니다)
  + 알림 하나 + 연결 결과 모달에 «이전 계정으로 예약해 둔 게시물 N개는 올리지 않았어요». ② 를 뒤에 하는 이유: 저장이 막히면(다른 핀치 사용자가 이미 연결한 계정 — 23505)
  계정은 그대로인데 예약만 떨어진다. 그 사이 크론이 집은 글은 엔진이 막는다. 같은 계정 재연결은 아무것도 바꾸지 않는다.
  연결 해제도 지운 계정을 대상이 빈 옛 글에 적는다(해제 → 다른 계정 연결 경로의 이력).
- **옛 발행 글 백필**: 매분 크론(`publish-processing`)이 본 작업을 끝내고 남는 시간에만 10건씩(`lib/publish/account-backfill.ts`).
  준비물을 만든 계정(`container_owner_id`)을 알면 그것을 적고, 모르면 지금 토큰으로 `GET /{게시물 id}?fields=username,permalink,owner` —
  내 글이면 지금 계정, 못 읽거나 없으면 이전 계정 표식(`__previous__`), 일시 오류는 `account_check_after` 로 미뤄 다음에.
  스레드는 고급 접근 승인 뒤 **남의 공개 글도 읽혀서** «읽혔다 = 내 글»이 아니다 — owner 가 오거나 아이디가 지금 계정과 같을 때만 내 글로 본다.
- **목록**: 모든 줄(달력 옆 날짜 칸·발행예약·발행완료·초안)에 채널 배지 옆 계정 칩 «@아이디». 지금 계정이 아니면 점선·«@옛 · 이전 계정»(표식은 «이전 계정»만).
  대상이 빈 안 나간 옛 글·초안은 지금 계정(거기로 간다). 대상이 빈 옛 발행 글은 백필 전까지 칩이 없다(모름). 「지금 발행」 확인 모달이 올라갈 계정을 말한다
  («이전 계정(@A)이 아니라 지금 연결된 @B 계정으로 올라가요»). 계정 필터는 넣지 않았다(칩으로 충분 — 필요하면 다음에).
- 알려진 한계: 백필에서 **지금 계정에서 지운 옛 글**도 «없다»로 답이 와 «이전 계정»으로 적힌다(메타가 두 경우를 구별해 주지 않는다).
  0094 이전에 계정을 두 번 이상 바꾼 사람의 옛 발행 글은, 다음 전환 때 «바로 전 계정»으로 적힐 수 있다(그보다 앞선 계정인지 알 방법이 없다).
- 검사: `node scripts/test-publish-account.ts`(판정·목록·백필·문구) · `test-publish-engine.ts`(«대상 계정» 절 — 448개 조합에서 메타를 부르지 않음).

     ① 0행 ② 0행 ③ INSERT 칸 6개(channel, caption, image_urls, scheduled_at, status, user_id)·UPDATE 칸 5개(caption, error, image_urls, scheduled_at, status)
     ④ create_publish_post 등 새 함수 다섯 개는 service_role 만 보여야 한다.
   - **0094(계정 전환)도 코드보다 먼저, 0093 다음에** 같은 방법으로 붙여 넣고 Run. 맨 아래 «적용 확인»: ① 새 칸 3개 ② 쓰기 칸이 0093 과 같음(INSERT 6개·UPDATE 5개, account_ 칸 없음) ③ 0행.
     적용 전에 새 코드가 나가면 목록이 «불러오지 못했어요»가 되고 발행 선점이 실패한다.
2. **Storage 전역 파일 크기 상한을 300MB 이상으로** — 반드시 1번 **다음에**.
   Supabase 대시보드 → 프로젝트 → **Storage → Settings**(주소 `https://supabase.com/dashboard/project/<프로젝트 ref>/storage/settings`)
   → **Global file size limit** 을 300 MB(이상)로 바꾸고 저장. (Supabase 문서 «File limits», 2026-09-12 확인 — Pro 는 500GB 까지, Free 는 50MB 까지)
   - 버킷 상한은 전역 상한을 넘지 못한다(낮은 쪽이 이긴다). 안 올리면 큰 영상 업로드가 Storage 에서 거절된다.
   - 순서가 중요한 이유: 0093 이 공개 버킷 세 개(cardnews·brand-logos·reference-thumbs)에 크기·형식 상한을 먼저 건다.
     전역 상한을 먼저 올리면 그 사이 로그인한 누구나 공개 버킷에 300MB 파일을 올릴 수 있다.
3. **환경 변수 — 새로 넣을 것은 없다.** 이미 쓰는 것이 Vercel 운영(Production)에 있는지만 확인한다:
   `SUPABASE_SERVICE_ROLE_KEY`(업로드 자리 발급·발행) · `CRON_SECRET`(크론 3개) · `TOKEN_ENCRYPTION_KEY`(연동 토큰) · `NEXT_PUBLIC_SUPABASE_URL` · `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
4. **합치고 배포** — 9/16~18 심사 녹화가 끝난 뒤(§4 «합치는 시점»). 배포 뒤 Vercel → 프로젝트 → Settings → Cron Jobs 에
   `/api/cron/publish-processing`(매분)·`/api/cron/publish-media-sweep`(매일 20:50 UTC)이 보이는지 본다. 매분 크론은 Pro 플랜이어야 돈다(지금 Pro).
5. **아래 «손으로 해 보는 시험»을 운영에서 한 번** — S0 실측(폰 원본)을 겸한다. 결과(통과·거절·처리 시간)를 이 문서에 적는다.
6. **되돌릴 때** — 이전 배포로 되돌리면(Instant Rollback) 크론은 안 돌아가 «처리 중» 글이 굳는다. 0093 맨 아래 «롤백 때» SQL 을 함께 실행한다.

## 손으로 해 보는 시험 (운영, 인스타·스레드가 연동된 계정)

준비물: 사진 JPG 2장(세로·가로), 아이폰 기본 카메라 영상(HEVC MOV, 10~30초), 갤럭시 MP4, 캡컷에서 내보낸 MP4, 화면 녹화 1개, 1분 넘는 영상 1개,
그리고 거절돼야 할 파일 — WEBM 1개, PDF 1개, 70초짜리 영상(스토리 상한 60초 확인용).
각 줄의 «→» 뒤가 기대 결과다. 어긋나면 그 줄 번호와 화면을 남긴다.

**A. 고르기·검사(작성기)** — 「새 게시물 포스팅」 → 채널 인스타그램. 파일 창은 맞는 형식만 보여 주므로 틀린 형식은 **사진 칸에 끌어 놓아** 넣는다.
1. PDF 1개 + JPG 11장을 한 번에 끌어 놓는다 → 오류 줄에 «형식이 맞지 않는 파일은 뺐어요 — …»와 «인스타그램은 사진·영상을 10개까지 올릴 수 있어요.» **두 문장이 함께**, 타일은 10개.
2. WEBM 만 끌어 놓는다 → «MP4·MOV 영상이나 JPG·PNG·WEBP 사진만 올릴 수 있어요.», 타일 없음.
3. 70초 영상 1개 + «스토리로 올리기» → 타일이 «보류»(올라가지 않음)와 이유 문구. 스토리를 끄면(릴스) → 그때 올라가기 시작한다.
4. 올리는 중 진행 막대가 움직이고, 창을 닫았다 다시 열면 올리던 파일은 버려진다(다시 골라야 한다).

**B. 인스타그램**
5. 사진 1장 → «지금 발행» → 결과 모달 «인스타그램에 올라갔어요» → 「발행완료」 탭에 «게시물 보기» → 눌러 인스타에서 확인.
6. 영상 1개(릴스) → «커버»에서 장면을 바꾸고 «피드에도 보이기» 켠 채 «지금 발행» → 결과 모달 «인스타그램이 영상을 처리하고 있어요» →
   목록 «처리 중» → 몇 분 안에 발행 + 알림 «게시물이 발행됐어요» → 인스타 앱에서 릴스 탭·피드 둘 다 보이고 커버가 고른 장면.
7. 6과 같게, «피드에도 보이기»만 끄고 → 릴스 탭에만 보인다.
8. 사진·영상 섞어 3개(순서 사진-영상-사진) → 캐러셀로 올라가고 순서가 같다.
9. 사진 1장 + «스토리로 올리기» → 글 칸에 «스토리에는 글이 올라가지 않아요» → 발행 → 목록 «스토리 보기». 영상 1개 스토리도 한 번.

**C. 스레드**
10. 글만 / 사진 1장 / 영상 1개 / 사진·영상 섞어 20개 — 네 번 발행 → 스레드 앱에서 각각 확인(20개 캐러셀은 순서까지).

**D. 예약·취소·실패**
11. 영상을 지금부터 25분 뒤로 «예약 발행» → 예약 시각 20분 전쯤부터 미리 준비하지만 목록엔 계속 «예약», **예약 시각 전엔 절대 안 올라간다** → 예약 시각 5분 안에 발행 + 알림.
12. 영상 «지금 발행» 직후 «처리 중»일 때 «발행 취소» → «취소됨», 인스타에 안 올라간다 → 취소된 글 «삭제».
13. 사진을 1시간 뒤로 예약 → 설정 > 채널에서 인스타 연결 해제 → 그 글이 곧바로 «실패»(«연결을 해제해서 발행하지 못했어요 — 다시 연결한 뒤 예약해 주세요»)
    → 다시 연결 → 실패 줄의 «지금 발행» → 올라간다(«다시 예약»으로 시각을 새로 잡아도 된다).
14. (선택, 수리 1 확인 — 시험용 글에만) 1분 넘는 영상을 «지금 발행»하고 «처리 중»인 동안 SQL Editor 에서
    `update public.scheduled_posts set processing_deadline = now() - interval '1 minute' where id = '<그 글 id>' and status = 'processing';`
    → 1분 안에 «…게시물을 처리하는 데 너무 오래 걸려요» 실패 + 알림 → 실패 줄의 «지금 발행» → **곧바로 또 실패하지 않고** «처리 중» 또는 «발행됨»이 된다.
    (그사이 메타 처리가 이미 끝났으면 실패 없이 바로 올라간다 — 그것도 통과다.)

**E. 파일·목록**
15. 사진 넣은 초안을 «삭제» → 몇 초 뒤 Storage → publish-media 버킷의 내 폴더에서 그 파일이 사라진다.
16. 발행 화면을 연 채 1시간 넘게 둔 뒤 달력↔목록을 오간다 → 깨진 그림 칸 대신 필름·그림 아이콘(수리 4).
17. 발행 7일 뒤(publish-media-sweep) 영상 원본은 지워지고 목록 썸네일(커버 JPEG)은 남는다 — 적용 1주 뒤 한 번 본다.

**F. 크론·예시 화면**
18. Vercel → Logs 에서 `/api/cron/publish-processing` 이 매분 200. 미리보기 배포에는 크론이 안 돈다 — 거기서 «처리 중»은 멈춰 보인다
    (손으로 부르려면 `Authorization: Bearer <CRON_SECRET>` 헤더로 그 주소를 GET).
19. 예시 화면(키 없는 미리보기)에서 올리기·저장·발행을 눌러 본다 → «지금은 예시 화면이라 …할 수 없어요.» — «데모 모드» 문구가 안 보인다.

**G. 계정 바꾸기(0094)** — 인스타 계정 두 개(A·B) 필요
20. A 로 연결 → 사진을 1시간 뒤로 예약 + 사진 1장 «지금 발행» → 목록 두 줄 모두 채널 배지 옆 «@A».
21. 설정 > 채널에서 인스타 «다시 연결»로 **B** 계정 로그인 → 연결 결과 모달에 «이전 계정으로 예약해 둔 게시물 1개는 올리지 않았어요…», 알림 하나 →
    발행 화면: 예약 글은 «실패»(«계정을 바꿔서 발행하지 못했어요 — …»)·칩 «@A · 이전 계정»(점선), 발행된 글도 «@A · 이전 계정».
22. 21의 실패 글에서 「지금 발행」 → 확인 모달 «이전 계정(@A)이 아니라 지금 연결된 @B 계정으로 올라가요» → B 에 올라가고 칩이 «@B».
    (또는 «다시 예약» → 칩 «@B» → 예약 시각에 B 로.)
23. 다시 A 로 연결 → 20에서 발행된 글의 칩이 이전 계정 표시 없이 «@A» 로 돌아온다. 같은 계정으로 다시 연결하면 아무 글도 멈추지 않는다.
24. (0094 전 글이 있는 계정) 배포 뒤 몇 분 → 옛 발행 글에 칩이 생긴다(백필 — Vercel Logs 의 publish-processing 응답 `backfill`).

## 2. 메타가 받는 것 (2026-09-11 문서 기준)

- **인스타 릴스**: `media_type=REELS` + `video_url`. MP4/MOV, H.264/HEVC + AAC, 3초~15분, 300MB 이하, 가로 1920px 이하. 커버 `cover_url`(JPEG) 또는 `thumb_offset`, `share_to_feed`.
  일반 피드 `VIDEO` 는 2023-11 부터 단일 게시물로는 안 된다(캐러셀 아이템으로만 남음).
- **인스타 스토리**: `STORIES` 사진·영상(영상 3~60초, 100MB 이하).
- **인스타 캐러셀**: 사진·영상 섞어 2~10개. 모든 아이템이 첫 아이템 비율로 잘린다.
- **스레드 영상**: `VIDEO` + `video_url`, 5분 이하·1GB 이하. 캐러셀은 사진·영상 섞어 2~20개.
- **하루 한도**: 인스타 `content_publishing_limit`(문서에 100·50 이 섞여 있다 — 실행 중에 `quota_total` 을 읽는다), 스레드 250개.
- **컨테이너 오류 코드**를 한국어로 바꿔 보여 준다: 인스타 2207026(형식)·2207052(파일 못 가져감)·2207003(다운로드 시간 초과), 스레드 `FAILED_DOWNLOADING_VIDEO`·`INVALID_DURATION`·`INVALID_FRAME_RATE`.

## 3. 설계 — 서버에서 영상을 변환하지 않는다

1. **브라우저 → Storage 직접 업로드.** 서버 액션이 경로(`${uid}/${uuid}.mp4`)를 정하고 **admin 클라이언트로 서명된 업로드 토큰**을 준다.
   브라우저는 TUS(이어받기, 6MB 조각)로 올린다 — 진행률이 보이고 끊겨도 이어진다(`tus-js-client` 새 의존성).
   올린 뒤 확인 액션이 크기·형식을 다시 보고 틀리면 지운다. ⚠️ `links/actions.ts` 의 `admin ?? createClient()` 폴백을 베끼지 말 것(CLAUDE.md 보안 규칙).
   **사진도 같은 길로 옮긴다** → 3MB 상한이 사라져 인스타 10장·스레드 20장 캐러셀이 실제로 된다.
2. **검사는 브라우저에서**: 확장자·MIME·크기·길이·해상도(`<video>` 메타데이터). 형식·코덱을 사용자에게 요구하고, 최종 판정은 메타가 한다.
   ⚠️ 폰 원본이 메타 조건(moov 앞쪽, edit list 없음)에 걸리는지는 확인 안 됨 — S0 실측으로 정한다.
3. **새 버킷 `publish-media`**: 파일 300MB, `video/mp4`·`video/quicktime`·`image/jpeg` 만, 로그인 사용자 insert 정책 없음(서버 토큰으로만).
   비공개 버킷 + 짧은 서명 URL 을 먼저 시험하고(메타가 쿼리 토큰 붙은 URL 을 받는지 미확인), 안 되면 `cardnews` 처럼 공개.
   Supabase **전역 파일 크기 상한을 대시보드에서 300MB 이상으로** 올려야 한다(Pro 는 500GB 까지, 현재 값 미확인). `cardnews` 에도 8MB·이미지만 제한을 건다.
4. **비동기 발행(크론 여러 번에 걸친 상태 기계)**: `scheduled → publishing → 컨테이너 생성 → (바로 끝나면) 발행 / (아니면) processing`.
   매분 도는 가벼운 크론 `publish-processing` 이 상태를 보고 FINISHED 면 발행, PUBLISHED 면 «이미 올라감»으로 기록(두 번 올리지 않기),
   ERROR/EXPIRED 면 한국어 사유로 실패. 마감은 컨테이너 생성 + 30분(컨테이너 수명 24시간).
   예약 영상은 예약 시각 15~30분 전에 컨테이너를 만들고, **예약 시각 전엔 절대 발행하지 않는다.**
5. **보안**: `scheduled_posts` 는 주인이 모든 칸을 바꿀 수 있다(RLS). 새 서버 전용 칸(컨테이너 id 등)은 0085 방식으로 권한을 빼고,
   사용자가 상태를 `publishing`·`processing`·`published` 로 옮기지 못하게 트리거를 건다(INSERT·UPDATE 둘 다). `run.ts` 는 미디어 URL 이
   우리 버킷·그 사용자 폴더인지 다시 확인한다.
6. **정리**: 발행 7일 뒤 영상 원본을 지운다(메타는 자기 사본을 갖는다, 목록용 커버 JPEG 는 남긴다). 계정 삭제(`lib/account/delete.ts`)·
   고아 점검 크론 버킷 목록에 새 버킷을 넣는다(두 곳 다 폴더 두 단계까지만 훑는다 — 경로 깊이를 지킬 것).

## 6. 따로 찾은 것

- 틱톡 소개 페이지(`app/(finch)/(marketing)/tiktok/page.tsx`)가 **없는 기능을 약속한다** — «틱톡 인사이트 기반 게시물 예약 발행»(틱톡 발행 어댑터 없음),
  «영상별 조회수·참여율»(틱톡 영상 데이터는 일부러 비워 둔다, `lib/data/live.ts`). 문구 정리 필요.
